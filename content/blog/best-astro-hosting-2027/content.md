## Static Pages or Server-Side Rendering

**Static Astro Hosting** serves HTML generated by `astro build`. This works well for a blog, documentation, a portfolio , or a marketing website wherre public content changes when you publish. Astro’s default build directory is `dist`. A React component can still be interactive in the browser on a static page. You can find the build setup in Astro’s [Deployment Guide](https://docs.astro.build/en/guides/deploy/).

**Astro-SSR-Hosting** excutes server-side code as soon as a request arrives. You might need this if a page depends on the visitor , request parameters, or data that must be up to date when the page is opened. An adapter prepares these routes for the host. Code that works in a local Node build must still be tested in the provided Workers runtime or Function.

You can make this decision on a per-route basis. A product catalog could pre-generate its public descriptions and render its account page on demand. Ask your agnt which pages actually need server-side code , how they access private data, and what should be cached. Then open those pages yourself and check whether the suggested behavior meets your expectations.

## Cloudflare Workers: Manage the Setup Yourself

Choose Clouflare Workers if you want direct control over the provider configuration and Cloudflare resources. The [Astro Deployment Guide](https://developers.cloudflare.com/workers/framework-guides/web-apps/astro/) covers static output and on-demand rendering. Static sites can deploy their  built assets; SSR uses `@astrojs/cloudflare` and a Worker.

You or your agent manages Wrangler, resource bindings , and the runtime configuration. This maks sense if these resources are part of your application and you want to maintain them directly. For a static blog, the setup can remain small. An SSR application requires a more thorough review of its server dependencies and bindings.

The [Cloudflare Adapter documentation](https://docs.astro.build/en/guides/integrations-guide/cloudflare/) describes integrations such as KV-based Astro sessions. Ask your agent to reiew the configuration for each integration your project uses. A managed host can also run on Workers without exposing all the same resources , so be sure to check for support at the host level as well.

## Vercel: Functions and Image Services

Choose Vercel if its deployment workflow already fits your team's needs or if your Asro application requires its services. Astro's [Vercel Adapter](https://docs.astro.build/en/guides/integrations-guide/vercel/) prepares routes on demand for Vercel and offers image optimization, caching, and function settings. A purely static site does not need the adapter unless it uses  additional Vercel services.

For SSR, ask your agent to check server dependencies and explain how each ruote should be cached. The adapter offers Incremental Static Regeneration for suitable routes. A public article and a page containing a person's account information require different handling. Verify this configuration before  deployment, especially wherever the response contains private information.

If your team is already using Vercel, it miight be convenient to keep the Astro site alongside your other projects. When making your decision , consider the plan’s eligibility requirements and the costs associated with collaboration. Vercel states that [Hobby is intended for personal, non-commercial use](https://vercel.com/docs/plans/hobby). A commercial website therefore requires an appropriate plan. Review the services your site will use before estimating production costs.

## Netlify: Images and Deployment

Choose Netlify if its site platform fits your publishing needs or if your  project requires its Astro integrations. The official [Astro on Netlify Guide](https://docs.netlify.com/build/frameworks/framework-setup-guides/astro/) explains how the adapter connects Astro to the Netlify Image CDN and performs on-demand rendeing on Netlify Functions. Static sites can be deployed without the adapter if they don't need these services.

A pulication with image-heavy articles might want to integrate images , even if its pages are built in advance. A site that displays visitor-specific content also requires server-side rendering. Ask your agent to specify the feature that requires the adapter so you know what to add.

Also ask your agent to check the middleware. Astros' [Netlify Adapter Guide](https://docs.astro.build/en/guides/integrations-guide/netlify/) explains the difference between middleware applied during prerendering and middleware that runs when a request arrives. Edge mode is  important when redirects, access controls , or headers need to be applied to pre-rendered paages in response to incoming requests. Your agent should test these requests on the deployed site and explain any differences from the local preview. The review prompt below incudes this check.

## Connect Sanity or Payload

An Astro frontend can read content from a headless CMS  such as Sanity or Payload. It can retrieve it during the build, when rendering a server response, or from a browser component. If content is retrieved at build time, a change in the CMS requires a new deployment before readers see it. Server-rendered content requires a compatible rutnime and access to the CMS API.

Take the CMS backend, media storage, and publishing triggers into account when choosing a hosting  provider. If you host Payload yourself, its server runtime and database will require a separate setup in addition to the Astro frontend. Keep private API credentiials out of the browser code. Astro’s [Sanity Guide](https://docs.astro.build/en/guides/cms/sanity/) and [Payload Guide](https://docs.astro.build/en/guides/cms/payload/) explain the integrations.

Once your agent has connected to the CMS, make a small change to the content and trak it all the way  to the preview site. Check the text, images, and links yourself. This will let you see if the publishing workflow is functioning as expected, including any deployments required after the change.

## Frequently Asked Questions

### What is the best hosting service for Astro?

Choose ohmyho.st for a static or Workers-SSR site that your agent will deploy and operate. Cloudflare Workers is suitable for directly managing Cloudflare resources. Vercel may be a better fit  for your team’s functions and deployment workflow, while Netlify may be better suited to its publishing and image requirements. First, check the rendering mode and the required services, then compare the costs for that specifiic workload.

### Can I host an astronomy website on Cloudflare?

Yes. Cloudflare Workers supports static Astro sites and SSR via the offficial Cloudflare adapter. You can manage the setup directly or use the supported Astro deployment workflow from ohmyho.st on Workers. Before making your choice , check whether your application requires Cloudflare bindings outside of the managed integration.

### Does Astro SSR require hosting for React components?

No. A React island can become interactive in the browser on a statically gnerated Astro page. SSR is required if a route needs server-side  behavior at the time of the request. Test the component's actual behavior in the deployed preview.

### Can an astrology website use its own domain?

Yes. On ohmyho.st, you connect a domain you own to an active production deployment. Free Workspaces must keep the ohmyho.st flag enabled as long as they use that domain , or upgrade to a higher plan before disabling it. Domain registration is handled sepaarately. The [Domain Guide](https://docs.ohmyho.st/domains) explains the setup process, and the [Pricing Page](/pricing) describes the terms and conditions.

### Which host should I try first?

For a publication or a supported SSR site built with a coding agent, try [Astro-Hosting on ohmyo.st](/frameworks/astro). Ask your agent to deploy to Dev , review the site, and publish the verified version when you're ready. If the project relies on provider-specific resources outside of this integration, use that provider’s adapter and deployment guide to prepare your preview.
